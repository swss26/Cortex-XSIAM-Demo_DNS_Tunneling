# DNS Tunneling C2 — Protocol Concept

> 개념 설명 문서입니다. 실행 가능한 코드는 포함하지 않습니다.
> DNS 터널 C2가 **왜 은신에 유리하고, 어떤 트래픽 특징을 남기는지**를 이해해 탐지에 활용하는 것이 목적입니다.

---

## 1. 왜 DNS인가

- 거의 모든 네트워크가 **아웃바운드 DNS(UDP 53)** 를 허용한다.
- 내부 클라이언트는 보통 로컬 리졸버로 질의하고, 리졸버가 재귀적으로 권한 서버까지 전달한다.
- 공격자가 특정 도메인(예: `example-c2.com`)의 **권한 네임서버**를 소유하면,
  그 도메인 하위 질의는 결국 공격자 서버로 도달한다 → **방화벽을 "정상 DNS"로 통과**.

```
[피해자 PC] → [사내 리졸버] → [루트/TLD] → [공격자 권한 NS = C2]
             \______________ 아웃바운드 53만 열려 있으면 성립 ______________/
```

---

## 2. 채널 구성 (레코드 타입 역할 분담)

DNS 터널은 하나의 53 채널을 **레코드 타입별로** 나눠 쓰는 경우가 많다.

| 단계 | 레코드 타입 | 방향 | 역할 |
|------|-------------|------|------|
| 핸드셰이크 | `NULL` (qtype 10) | C ↔ S | 세션 수립, keepalive |
| 명령 하달 | `CNAME` / `TXT` | S → C | Base32/Base64 인코딩된 명령 |
| 결과 유출 | `A` | C → S | 서브도메인 레이블에 데이터 청크 삽입 |

> 실제 구현마다 사용하는 레코드 타입은 다르다(TXT 전용, A 전용 등). 핵심은 **질의 이름(QNAME)과
> 응답 데이터에 페이로드를 실어 나른다**는 점이다.

---

## 3. 인코딩 · 청크 분할

DNS는 사용할 수 있는 문자와 길이에 제약이 있어, 페이로드를 아래 규칙으로 변환한다.

- **인코딩**: 주로 **Base32** (문자 집합 `A–Z`, `2–7` — DNS 레이블에 안전).
  Base64는 대소문자·`/`·`+` 때문에 회피형에서만 제한적으로 사용.
- **레이블 길이 제한**: 단일 레이블 ≤ **63자**, 전체 이름 ≤ **255자**.
- **청크 분할**: 데이터를 50자 안팎으로 잘라 여러 질의로 나눠 보낸다.
  순서 복원을 위해 세션ID / 전체청크수 / 인덱스를 이름에 포함한다.

개념적 질의 형태(값은 예시):

```
# 결과 유출 (C → S) : A 레코드
r.<sessionID>.<total>.<index>.<base32chunk>.<c2-domain>

# 명령 폴링 (C → S) : TXT 질의 → 응답에 명령
poll.<sessionID>.<c2-domain>   →  TXT: <base32(command)>
```

## 4. 남기는 트래픽 특징 (→ 탐지 포인트)

| 특징 | 정상 DNS | 터널 C2 |
|------|----------|---------|
| 레코드 타입 분포 | A/AAAA 위주 | NULL/TXT/CNAME 비정상 다수 |
| 질의 빈도 | 산발적 | 짧은 주기로 규칙적 폴링 |
| 서브도메인 길이/엔트로피 | 짧고 사전적 | 길고 무작위(고엔트로피) |
| 고유 서브도메인 수 | 도메인당 소수 | 한 도메인에 수천 개 유니크 라벨 |
| 업/다운 데이터 비율 | 균형 | 유출 방향(업링크) 편향 |

이 특징들이 **`detection/`** 의 XQL·Sigma 룰이 노리는 신호다.
